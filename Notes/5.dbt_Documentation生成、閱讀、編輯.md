## 1. 為什麼需要 dbt 文件？

### 🏢 團隊協作的挑戰
在資料團隊的日常工作中，常見以下問題：

| 挑戰 | 影響 | 傳統解決方式的問題 |
|------|------|-------------------|
| **多人分工** | 團隊成員不了解彼此的工作內容 | 手動製作文件耗時費力 |
| **資訊孤島** | 知識無法有效流通和共享 | 文件更新困難，容易過時 |
| **知識流失** | 人員異動時，重要資訊遺失 | 維護成本高，難以持續 |

### 💡 dbt 文件的解決方案

#### 🚀 核心優勢
- **自動化生成**：一個指令完成所有文件產出
- **即時同步**：程式碼變更時文件自動更新
- **零維護負擔**：不需要額外的文件維護工作
- **豐富內容**：包含完整的技術資訊和關聯圖

> **關鍵理解**：dbt 文件不是「額外的工作」，而是「自動產生的副產品」

## 2. dbt 文件的核心功能

### 📚 自動包含的內容

#### 🔧 技術物件
- **Models**：資料模型的 SQL 語法和結構
- **Macros**：可重複使用的程式碼片段
- **Seeds**：種子資料檔案內容

#### 📊 資料結構
- **欄位資訊**：每個欄位的名稱、類型、說明
- **Lineage Graph**：資料血緣關係圖
- **測試結果**：資料品質測試狀態

#### 📝 業務說明
- **Model 說明**：可自定義的模型用途描述
- **欄位註解**：業務欄位的詳細說明
- **標籤分類**：便於分類和搜尋

### 🎨 文件特色
- **互動式介面**：可點擊瀏覽的網頁格式
- **搜尋功能**：快速定位所需資訊
- **視覺化呈現**：圖形化的資料關聯展示

## 3. 開發環境文件操作

### ⚡ 快速生成文件

#### 指令執行
```bash
dbt docs generate
```

這個指令會：
1. 掃描專案中的所有 dbt 物件
2. 分析程式碼結構和關聯性
3. 生成靜態文件檔案

#### 📱 檢視文件
執行完成後，在 Cloud IDE 中：
1. 點選 **View Docs**（通常在branch 名稱旁）
2. 開啟最新產出的文件網頁
3. 即可瀏覽完整的專案文件

### 🔄 開發流程整合
```mermaid
    A[編寫程式碼] --> B[執行 dbt docs generate]
    B --> C[檢視 View Docs]
    C --> D[驗證文件內容]
    D --> A
```

## 4. 正式環境文件設定

### 🏗️ Job 設定流程

#### Step 1: 編輯現有 Job
1. 進入 Job 管理頁面
2. 選擇目標 Job（如：Default Build）
3. 點選 **Settings** → **Edit**

#### Step 2: 啟用文件生成
在 **Execution Settings** 中 勾選 Generate docs on run：
```
☑️ Generate docs on run: Automatically generate updated project docs each time this job runs
```

#### Step 3: 儲存設定
點選 **Save** 完成設定

### 🚀 執行與驗證

#### 執行 Job
1. 回到 Job 頁面
2. 點選 **Run Now**
3. 觀察執行步驟

#### 📊 執行結果確認
執行完成後會看到額外步驟：
```
✅ Invoke dbt docs generate
```

### ⚙️ 文件來源設定

#### 配置文件來源
1. 進入 **Project Settings**
2. 選擇 **Artifacts** → **Documentation**
3. 選擇設定好的 Job（如：Default Build）

#### 🎯 設定完成後
可在上方選單的 **Documentation** 查看正式環境文件

## 5. 文件檢視與管理

### 🌍 環境差異理解

| 環境類型 | 檢視方式 | 更新時機 | 適用場景 | 內容同步 |
|----------|----------|----------|----------|----------|
| **開發環境** | Cloud IDE 內的 View Docs | 手動執行 `dbt docs generate` | 開發測試、即時查看 | 包含未提交的變更 |
| **正式環境** | 上方選單 Documentation | Job 執行時自動更新 | 團隊共享、正式參考 | 僅顯示已合併到 main 的內容 |

> **重要提醒**：開發環境的異動若未提交到 GitHub 並合併到 main branch，不會出現在正式環境文件中

### 📚 文件結構解析

#### 🗂️ 主要頁籤分類
dbt 文件主要分為兩個頁籤：

| 頁籤 | 內容 | 說明 |
|------|------|------|
| **Project** | dbt 專案物件 | 我們建立的 models、macros、seeds |
| **Database** | 資料庫物件檢視 | databases、datasets、tables/views |

#### 📊 Project 頁籤內容
- **Sources**：外部資料源（如官方提供的 BigQuery datasets）
- **Project**：我們的 dbt 專案物件

### 🔍 模型文件詳細內容

當點選任一 model 時，可以看到以下資訊區塊：

#### 📋 Details 區塊
顯示 model 的基本資訊：
- 模型類型（table/view）
- 建立時間
- 相關設定

#### 📝 Description 區塊
model 的業務說明（可自定義）

#### 📊 Columns 區塊
自動產生的欄位資訊：
- **欄位名稱**：資料庫中的實際欄位名
- **欄位型態**：資料類型（string、integer 等）
- **測試狀態**：顯示相關的 dbt tests
- **欄位說明**：可自定義的業務描述

#### 🔗 Referenced By 區塊
- 顯示參考此 model 的下游物件
- 有助於了解資料影響範圍

#### ⬆️ Depends On 區塊
- 顯示此 model 依賴的上游物件
- 追蹤資料來源和依賴關係

#### 💻 Code 區塊
提供兩種檢視方式：
- **Source**：原始 SQL 程式碼
- **Compiled**：dbt 編譯後的實際執行語法

#### 🌐 Lineage Graph
- 點選右下角藍綠色按鈕開啟
- 圖形化展示上下游關係
- 支援全螢幕檢視（View Fullscreen）

### 📈 文件使用最佳實踐

#### 🔍 有效利用文件
1. **新人入職**：透過 Lineage Graph 快速了解專案結構
2. **程式碼 Review**：檢查 Code 區塊的 SQL 邏輯
3. **業務溝通**：使用 Description 向非技術人員解釋資料流程
4. **問題排查**：透過 Depends On 和 Referenced By 追蹤資料流向
5. **測試驗證**：在 Columns 區塊檢查測試執行狀態

#### 📝 文件品質提升策略
- **環境管理**：開發時用開發環境文件，正式溝通用正式環境文件
- **即時更新**：開發階段頻繁執行 `dbt docs generate` 確保文件同步
- **完整說明**：為所有重要模型和欄位添加 Description

## 6. 自定義文件說明

### 📝 為什麼要添加說明？
雖然 dbt 自動生成技術文件，但業務脈絡和邏輯說明仍需手動補充：

| 自動生成內容 | 需要手動補充 | 價值 |
|-------------|-------------|------|
| 欄位名稱、型態 | 業務意義、計算邏輯 | 讓非技術人員理解 |
| SQL 語法 | 業務背景、使用場景 | 提升團隊協作效率 |
| 資料關聯 | 重要注意事項 | 避免誤用或誤解 |

### ⚙️ 添加說明的方法

#### 📍 在 schema.yml 中定義
在現有的 `models/schema.yml` 檔案中，只需要在 model 和 column 下方加入 `description` 即可。

#### 📋 完整範例配置
```yaml
version: 2

models:
  - name: customers
    description: One record per customer  # Model 層級說明
    columns:
      - name: customer_id
        description: Primary key  # 欄位層級說明
        tests:
          - unique
          - not_null
      - name: first_order_date
        description: NULL when a customer has not yet placed an order.

  - name: stg_customers
    description: This model cleans up customer data
    columns:
      - name: customer_id
        description: Primary key
        tests:
          - unique
          - not_null

  - name: stg_orders
    description: This model cleans up order data
    columns:
      - name: order_id
        description: Primary key
        tests:
          - unique
          - not_null
      - name: status
        description: Order status tracking field
        tests:
          - accepted_values:
              values: ['placed', 'shipped', 'completed', 'return_pending', 'returned']
      - name: customer_id
        description: Foreign key to customers table
        tests:
          - not_null
          - relationships:
              to: ref('stg_customers')
              field: customer_id
```

### 🔄 更新文件流程

#### Step 1: 編輯 schema.yml
在適當位置加入 `description` 欄位

#### Step 2: 重新生成文件
```bash
dbt docs generate
```

#### Step 3: 檢視更新結果
在文件中確認說明已正確顯示

### ✍️ 撰寫說明的最佳實踐

#### 📊 Model 說明撰寫要點
- **用途說明**：這個模型的主要功能
- **資料範圍**：包含什麼時間範圍或條件的資料
- **更新頻率**：資料更新的時機
- **注意事項**：使用時需要注意的重點

**範例**：
```yaml
description: |
  客戶主檔，每個客戶一筆記錄。
  包含客戶基本資訊和首次訂單日期。
  每日凌晨 2:00 自動更新。
```

#### 🏷️ 欄位說明撰寫要點
- **業務意義**：這個欄位代表什麼業務概念
- **計算邏輯**：如果是計算欄位，說明計算方式
- **特殊值處理**：NULL 值或特殊情況的意義
- **使用建議**：建議的使用方式或注意事項

**範例**：
```yaml
- name: first_order_date
  description: |
    客戶首次下單日期。
    若客戶尚未下單則為 NULL。
    可用於計算客戶生命週期分析。
```

### 🎯 投資報酬率思考

#### 💰 付出成本
- **時間投入**：撰寫和維護說明文字
- **標準化**：建立團隊撰寫規範

#### 🚀 獲得效益
- **減少溝通成本**：減少重複解釋相同概念
- **提升新人效率**：快速了解業務邏輯
- **降低錯誤風險**：減少因誤解而產生的錯誤
- **知識保存**：建立可持續的知識庫

> **關鍵理念**：雖然手動編輯需要投入時間，但能大幅提升團隊協作效率，長期來看是值得的投資。

## 7. 常見問題與最佳實踐

### ❓ 常見問題解答

#### Q1: 文件沒有顯示最新內容？
**解決方案**：
- 開發環境：重新執行 `dbt docs generate`
- 正式環境：確認 Job 設定正確且最近有執行

#### Q2: 正式環境文件顯示空白？
**檢查清單**：
1. ✅ Job 是否啟用 "Generate docs on run"
2. ✅ Project Settings 是否設定正確的 Job
3. ✅ Job 是否成功執行過

#### Q3: 開發環境和正式環境的文件內容不一致？
**原因分析**：
- 開發環境包含未提交的變更
- 正式環境僅顯示已合併到 main branch 的內容

**解決方案**：
1. 確認變更已提交並合併到 main branch
2. 確認正式環境的 Job 已重新執行
3. 檢查 Project Settings 的文件來源設定

### 🎯 最佳實踐建議

#### 1. 設定策略
- **自動化優先**：盡量在 Job 中自動生成文件
- **雙環境維護**：開發和正式環境都要有文件

#### 2. 團隊協作
- **文件優先**：遇到問題先查文件再問人
- **持續改善**：定期檢討文件完整性
- **知識分享**：將文件作為培訓教材

#### 3. 文件品質維護
- **完整說明**：為重要模型和欄位添加有意義的 description
- **定期更新**：隨著業務邏輯變化更新說明
- **標準化撰寫**：建立團隊的文件撰寫規範
- **版本同步**：確保開發和正式環境的內容一致性

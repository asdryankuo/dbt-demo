# dbt run 與 Materializations 入門指南

## 🤔 問題起點：我的 Model 跑到哪裡去了？

### 情境描述
我們在 dbt Cloud 建立了 `customers` model，它整合了：
- 客戶基本資料
- 每位客戶的第一次消費日期
- 最近消費日期
- 總訂單數量

**但是問題來了**：這些邏輯寫好了，要怎麼在 BigQuery 看到實際的資料呢？

### 核心概念
> dbt 只是**描述**了資料轉換的邏輯，但還沒有**執行**這些邏輯。就像你寫了一份食譜，但還沒有真正下廚一樣。

## 🚀 dbt run：將邏輯變成真實資料

### 什麼是 dbt run？
`dbt run` 是 dbt 的核心指令，它的作用是：
- 讀取你寫的 `.sql` 檔案
- 按照依賴順序執行 SQL
- 在目標資料庫（BigQuery）中建立實際的 table 或 view

### 實際操作

#### 1. 執行指令
```bash
dbt run
```

#### 2. 檢查執行結果
執行完成後，你會看到類似這樣的輸出：
```
Completed successfully

Done. PASS=3 WARN=0 ERROR=0 SKIP=0 TOTAL=3
```

#### 3. 查看詳細 Log
點擊 log 可以看到 dbt 做了什麼：
- 建立了 `dbt_dev.stg_customers` view
- 建立了 `dbt_dev.stg_orders` view  
- 建立了 `dbt_dev.customers` view

#### 4. 在 BigQuery 驗證
回到 BigQuery，你會發現：
- 新的 dataset：`dbt_dev`（這是我們在專案設定時指定的）
- 三個新的 views：對應我們的三個 models

## 📊 Materializations：決定資料的「形態」

### 什麼是 Materialization？
Materialization 決定了你的 model 在資料庫中會以什麼形式存在：

```
SQL Logic (你寫的 .sql 檔案)
         ↓ dbt run
Database Object (View 或 Table) 預設為 view
```

### 四種 Materialization 類型

#### 1. View（預設）
```sql
-- 實際上在 BigQuery 建立的是：
CREATE VIEW dbt_dev.customers AS (
    -- 你的 SQL 邏輯
)
```

**特性：**
- ✅ 不佔用儲存空間
- ✅ 資料永遠是最新的
- ❌ 每次查詢都要重新計算，速度較慢
- ❌ 複雜查詢可能很耗資源

#### 2. Table
```sql
-- 實際上在 BigQuery 建立的是：
CREATE TABLE dbt_dev.customers AS (
    -- 你的 SQL 邏輯，結果會被儲存
)
```

**特性：**
- ✅ 查詢速度快
- ✅ 適合複雜計算的結果
- ❌ 佔用儲存空間
- ❌ 資料有時間差（需要重新執行才會更新）

#### 3. Incremental（進階）
- 只處理新增或異動的資料
- 適合大型資料表

#### 4. Ephemeral（進階）
- 不在資料庫建立物件
- 只用於中間邏輯

## ⚙️ 如何設定 Materialization

### 方法一：單一 Model 設定

在 model 檔案的最上方加入：
```sql
{{ config(materialized="table") }}

with customers as (
    select * from {{ ref('stg_customers') }}
),
-- 其他邏輯...
```

**執行 dbt run 後的變化：**
- 原本：CREATE VIEW
- 現在：CREATE TABLE

### 方法二：專案層級設定

在 `dbt_project.yml` 中設定：
```yaml
models:
  jaffle_shop:           # 你的專案名稱
    materialized: table  # 所有 models 預設為 table
    staging:
      materialized: view # staging 資料夾下的 models 為 view
```

**階層式設定優先順序：**
```
Model 層級設定 > 資料夾層級設定 > 專案層級設定 > dbt 預設
```

## 🔍 實際操作流程

### 步驟 1：修改單一 Model
```sql
-- models/customers.sql
{{ config(materialized="table") }}

with customers as (
    select * from {{ ref('stg_customers') }}
),
-- 其他邏輯保持不變...
```

### 步驟 2：執行並驗證
```bash
dbt run
```

查看 log 會顯示：
```
CREATE TABLE `dbt-tutorial.dbt_dev.customers`
```

### 步驟 3：專案層級設定
```yaml
# dbt_project.yml
models:
  jaffle_shop:
    materialized: table
```

### 步驟 4：再次執行
```bash
dbt run
```

所有 models 都會變成 table。

## 🤔 View vs Table：何時使用？

### 使用 View 的情況
- 📊 **資料量小**：查詢速度影響不大
- 🔄 **需要即時資料**：如監控儀表板
- 💾 **節省儲存成本**：不想佔用額外空間
- 🧪 **開發測試階段**：快速迭代，不需要持久化

### 使用 Table 的情況
- 📈 **資料量大**：避免重複計算複雜邏輯
- ⚡ **查詢效能重要**：使用者需要快速回應
- 📅 **分析報表**：資料不需要即時更新
- 🏗️ **生產環境**：穩定的資料產品

## 🎯 實務建議

### 開發最佳實踐

#### Materialization 策略
```yaml
# 建議的專案設定
models:
  jaffle_shop:
    staging:
      materialized: view      # staging 用 view，節省空間
    marts:
      materialized: table     # 分析層用 table，提升效能
```

#### 開發流程
1. **開發階段**：全部用 view（快速迭代）
2. **測試階段**：重要 models 改為 table（驗證效能）
3. **生產階段**：依需求分別設定

### 常見錯誤與解決

#### 錯誤 1：Materialization 設定語法錯誤
```sql
❌ {{ config(materialized=table) }}      # 缺少引號
✅ {{ config(materialized="table") }}    # 正確
```

#### 錯誤 2：YAML 縮排錯誤
```yaml
❌
models:
jaffle_shop:                    # 縮排錯誤
materialized: table

✅  
models:
  jaffle_shop:                  # 正確縮排
    materialized: table
```

#### 錯誤 3：忘記 dbt run
- 修改 materialization 後，必須執行 `dbt run` 才會生效
- BigQuery 中的物件不會自動更新

## 📈 效能考量

### View 的效能陷阱
```sql
-- 如果這個 view 被多次查詢，每次都會重新執行底層邏輯
CREATE VIEW complex_analysis AS (
    SELECT 
        customer_id,
        -- 複雜的統計計算...
        COUNT(*) OVER (PARTITION BY region) as regional_customer_count,
        -- 更多複雜邏輯...
    FROM large_table
    -- 複雜的 JOIN...
)
```

### Table 的儲存成本
- BigQuery 按儲存量收費
- 大型 table 會產生顯著成本
- 需要在效能和成本間平衡

你只需要告訴 dbt 要什麼結果，它會幫你處理如何建立和維護這些資料物件。
